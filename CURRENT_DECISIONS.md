# Current decisions

**Spec:** `0.5-demo`
**Status:** authoritative active decisions

- Release sequence is **local hosting first** (`0.5.0-local-rc.3`). Target VPS, public TLS/WSS, target-host provider smokes, and WebKit acceptance are later gates; local evidence must not be presented as target-host evidence. Prior `0.5.0-local-rc.2` remains the rollback image.
- On landing entry the browser makes exactly one automatic playback attempt for the committed, product-owned same-origin proactive MP3. Before both consents this path performs no conversation REST, WebSocket, microphone, provider, or session action. Autoplay block or media error exposes `Включить приветствие`; real session start stops/releases the greeting.
- The proactive MP3 is generated only by the explicit admin opt-in OpenRouter script and then committed as a static product asset. Its fixed product copy contains no visitor input or visitor data; ordinary visits never synthesize it.
- OpenRouter is the **only** STT and TTS provider/gateway after consent. One backend-only `OPENROUTER_API_KEY` authorizes both; the browser never receives credentials or calls OpenRouter directly.
- Authoritative pipeline: **browser PCM16 chunks → gateway/utterance assembler bounds mono PCM16 and emits one validated WAV → atomic `audio/wav` `SttPort` request → OpenRouter audio-input chat completion final transcript → Codex subscription / `gpt-5.6-luna` → OpenRouter TTS complete MP3 segment**.
- STT is one atomic phrase-level native `fetch` to `/api/v1/chat/completions` after end-of-turn / `audio.commit`, with base64 `input_audio`, format `wav`, and configurable default model `openai/gpt-audio-mini`. The only STT text event is `transcript.final`.
- `SttPort` is provider-neutral: one request carries a bounded, validated `audio/wav` payload and returns one final result. Browser-to-backend microphone transport remains chunked PCM16; the gateway/utterance assembler alone builds the WAV. `OpenRouterSttAdapter` validates and bounds the already-WAV bytes, base64-encodes them without conversion, applies request timeout/retry, and suppresses aborted or stale results.
- TTS uses native Bun `fetch` to `/api/v1/audio/speech`, model `x-ai/grok-voice-tts-1.0`, voice `eve`, and complete MP3 phrase segments. `TtsPort` remains provider-neutral; playback is ordered, cancellable, generation-filtered, and can degrade to text-only output.
- Phrase-level STT adds end-of-turn upload/inference latency. Each utterance is capped at 60 seconds and the WAV request at 2,000,000 bytes. The circular UI countdown comes from accepted 16 kHz PCM16 samples and the stricter server-advertised duration/byte ceiling, not wall time.
- Provider-neutral `visitor.text.submit` carries one bounded final typed turn. It supersedes uncommitted microphone bytes, is sequence/idempotency guarded, emits only a server-accepted `transcript.final`, and then follows the same Luna/state/tool/persistence semantics as speech. The in-chat booking form appears only at server-owned `COLLECT_BOOKING` and serializes fields as visitor text rather than invoking tools.
- Booking requires name, company, working email, phone or Telegram, consent, and exactly one of two server-supplied structured 20-minute `Europe/Moscow` candidates. All candidates are non-today weekdays on the 20-minute grid from 09:00 through 17:00 starts and exclude committed internal starts. The default pair is one morning plus one evening option. Typed and spoken bounded Russian morning/day/second-half/evening preferences refresh context; selection returns two in-band starts roughly one hour apart and rolls to a later weekday when needed, while explicit rejection excludes the rejected band. These are two current internal alternatives, never all global availability. Luna receives current Moscow date/day, preference state, and two labels; non-candidate tool slots are rejected.
- Booking is committed before optional qualification. The user-facing confirmation asks exactly `Можно задать два коротких вопроса?`; only a later explicit consent grants access. The server then deterministically asks monthly inbound leads first and integer `salesManagerCount` second, one at a time, and marks complete only when both are stored. Both-at-once completes; refusal with zero answers is skipped, refusal after one is partial, and booking remains booked. STT or TTS retries/failures never repeat Luna, business tools, or notifier side effects.
- Sales cadence is moderately proactive: no more than two discovery questions before a soft demo/meeting offer. The 10–15 million RUB/month claim is allowed only as an attributed claim from the user-provided Botamin brief and never as a guarantee, forecast, or transferable result.
- Prompts remain Markdown, the app remains one TypeScript full-stack Compose deployment, and no real calendar event, external availability check, or invitation is created.
- The supported local entrypoint is `scripts/deploy-local.sh` at `http://localhost:5173`. It materializes file-backed Compose secrets; Codex device auth persists in the fixed `botamin-codex-home` volume. Do not source `.env` or expose provider credentials through browser/build configuration.
