# Current decisions

**Spec:** `0.5-demo`
**Status:** authoritative active decisions

- Release sequence is **local hosting first**. `v0.5.0-local-rc.4` is recommended but pending; no tag, PR, or release hash is claimed here. RC3 evidence remains historical and separate. Target VPS, public TLS/WSS, target-host provider live booking, and WebKit full-journey acceptance are external gates; local evidence must not be presented as target-host evidence.
- On landing entry the browser makes exactly one automatic playback attempt for the committed, product-owned same-origin proactive MP3. Before both consents this path performs no conversation REST, WebSocket, microphone, provider, or session action. Autoplay block or media error exposes `Включить приветствие`; real session start stops/releases the greeting.
- The proactive MP3 is generated only by the explicit admin opt-in OpenRouter script and then committed as a static product asset. Its fixed product copy contains no visitor input or visitor data; ordinary visits never synthesize it.
- OpenRouter is the **only** STT and TTS provider/gateway after consent. One backend-only `OPENROUTER_API_KEY` authorizes both; the browser never receives credentials or calls OpenRouter directly.
- Authoritative pipeline: **browser PCM16 chunks → gateway/utterance assembler bounds mono PCM16 and emits one validated WAV → atomic `audio/wav` `SttPort` request → OpenRouter audio-input chat completion final transcript → Codex subscription / `gpt-5.6-luna` → OpenRouter TTS complete MP3 segment**.
- STT is one atomic phrase-level native `fetch` to `/api/v1/chat/completions` after end-of-turn / `audio.commit`, with base64 `input_audio`, format `wav`, and configurable default model `openai/gpt-audio-mini`. The only STT text event is `transcript.final`.
- `SttPort` is provider-neutral: one request carries a bounded, validated `audio/wav` payload and returns one final result. Browser-to-backend microphone transport remains chunked PCM16; the gateway/utterance assembler alone builds the WAV. `OpenRouterSttAdapter` validates and bounds the already-WAV bytes, base64-encodes them without conversion, applies request timeout/retry, and suppresses aborted or stale results.
- TTS uses native Bun `fetch` to `/api/v1/audio/speech`, model `x-ai/grok-voice-tts-1.0`, voice `eve`, and complete MP3 phrase segments. TTS input redacts contacts by default. The only contact exception requires active contact-processing consent and an exact server-approved email, phone, or Telegram value from accepted durable draft facts or the committed booking; arbitrary/model-supplied contacts stay redacted.
- Phrase-level STT adds end-of-turn upload/inference latency. Each utterance is capped at 60 seconds and the WAV request at 2,000,000 bytes. The circular UI countdown comes from accepted 16 kHz PCM16 samples and the stricter server-advertised duration/byte ceiling, not wall time.
- Provider-neutral `visitor.text.submit` carries one bounded final typed turn. It supersedes uncommitted microphone bytes, is sequence/idempotency guarded, emits only a server-accepted `transcript.final`, and follows the same fact extraction, Luna, state, tool, persistence, assistant, and optional TTS path as speech.
- RC4 uses one durable `conversation_contexts` row per conversation: nonnegative `revision`, validated `draft_json`, and matching `updated_at`. The JSON object contains the fact registry/provenance/conflicts, exactly two candidate identities, selected candidate, readiness, confirmation and commit states, and booking identity. Browser projections strip provenance/evidence. Mutations use `BEGIN IMMEDIATE`, expected-revision compare-and-swap, bounded conflict options, and idempotent form/conflict/confirmation requests.
- The in-chat form is a structured, server-stage-gated client of that same draft. It submits only field patches plus a current candidate identity through `booking.form.submit`; it does not fabricate a booking or bypass spoken/text facts. Conflicts require explicit selection, changed candidates require reselection, and exact-revision `booking.draft.confirm` is required before automatic commit.
- Booking requires accepted name, company, working email, phone or Telegram, consent, and exactly one of two server-supplied structured 20-minute `Europe/Moscow` candidates. Candidates always carry a concrete date/time, are non-today weekdays on the 20-minute grid from 09:00 through 17:00 starts, and exclude committed internal starts. Typed and spoken bounded Russian time-band and supported concrete date/time requests use the same server parser. These are current internal alternatives, never all global availability; non-candidate or stale selections are rejected.
- Exact draft confirmation automatically commits one durable booking and publishes one server-derived `internal_virtual` meeting projection with `status=scheduled`, `externalCalendarEventCreated=false`, and `externalInviteSent=false`. The final browser widget renders only from this projection after durable commit. No duplicate meeting table, external calendar availability call, event, invitation, or CRM record is created.
- Optional qualification starts directly after truthful meeting confirmation, without the retired separate permission question. The server asks only the first missing fact: monthly lead/contact volume before `salesManagerCount` when both are absent, only the missing field when one is known, and no question when both are known. Both-at-once completes; refusal with zero answers is skipped, refusal after one is partial, and the scheduled meeting remains intact.
- Sales cadence is moderately proactive: no more than two discovery questions before a soft demo/meeting offer. The 10–15 million RUB/month claim is allowed only as an attributed claim from the user-provided Botamin brief and never as a guarantee, forecast, or transferable result.
- Prompts remain Markdown and the app remains one TypeScript full-stack Compose deployment. The supported local entrypoint is `scripts/deploy-local.sh` at `http://localhost:5173`; it materializes file-backed secrets, takes a protected backup of an existing DB, drains/stops a running app before migration, migrates through normal `AUTO_MIGRATE=true` startup, waits for readiness, and runs the PII-safe RC4 schema/invariant check. Do not source `.env` or expose provider credentials through browser/build configuration.
